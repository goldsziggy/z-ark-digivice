# Local development service

Run `npm run build` and `npm start` at the repository root using Node 24. The service defaults to **127.0.0.1:8787**; `PORT` changes its port. An explicitly configured LAN development mode is described below; it was not enabled by this implementation task. The game uses Node built-ins and the compiled `build/digivice-core` executable. The optional Garage connector reuses the already-installed S3 SDK and existing server credentials; it is not required to play. No new cloud account, database server or production secret is required. `NODE_ENV=production` is deliberately refused.

The browser preview and this service are one local origin. This is a runnable development pairing and sync flow. Physical ESP devices and phones cannot connect over Wi-Fi to the default loopback listener. Opt-in LAN mode permits existing identities and bounded device asset reads on one private interface; network enrollment, TLS, physical presence confirmation, credential revocation and production firmware key storage remain future work.

All POST requests require `Content-Type: application/json`. Unknown fields are rejected. Errors have `{ "error": "stable_code", "message": "human explanation" }`. Bearer tokens must never be put in query strings or logs.

The web UI and its explicitly listed local JavaScript modules are served, including the local personal-art importer. Local personal directories and the browser’s separate personal-art database are never exposed as static paths or uploaded by the browser. The authenticated per-form route below serves only explicitly indexed, audited local pack/provenance pairs. Explicitly configured, pinned Garage objects have their separate authenticated download routes. Source, saves, arbitrary paths and GPS route uploads have no endpoint. Default mode refuses non-loopback hosts and peers; explicit LAN mode uses the bounded allowlists below. Unapproved origins and cross-site fetch metadata are refused in both modes. No permissive CORS response is enabled.

An event is exactly `{type,value}`. `starter-offer-seed` accepts a nonzero unsigned 32-bit integer only for an egg whose offers are still unset; the browser uses the server-generated offer endpoint above. Types `feed`, `play`, `rest`, `attack`, `heavy`, `magic`, and `capture` require `value:0`; `walk` requires an integer 1–1000; `card` requires 1 or 2; `select` requires an owned stable member ID from 1 through 4,294,967,294; `party-add` and `party-remove` use that same ID range with the Home-only XP companion rules below; `release` uses the same ID range and requires a nonactive owned member at home or during a rules-10 through rules-15 wild encounter; `hatch` accepts fixed starter IDs 1–8, or saved offer slots 9–11, and requires an incomplete egg state; `mode` takes 0 for Tactical or 1 for Auto and is available only at home; `auto-fight` requires value 0 and an Auto encounter not already awaiting capture; `auto-resume` requires value 0 and a saved Auto capture pause; historical `auto` requires value 0 and an Auto encounter without a pending capture pause; `evolve` requires a supported native form ID from 1 through 512, a completed partner at home and its native branch requirements. `attack` is the physical move. Selecting a member is available at home. The active member’s care values are projected into the familiar top-level state fields; selection preserves each member’s individual state. The bounded collection, `activeCreatureId`, `wildSpecies`, `wildName`, and `legacyCaptures` are returned with every current state. The C++ game core validates context as well: care at home, battle actions during encounters, and manual capture only when the wild creature is weakened in Tactical mode. Auto encounters reject manual attack, card and capture events. Invalid histories return 422 without changing the save. Walk and card inputs are simulated or client-reported observations, **not proof** that steps occurred or a real NFC card was present.

New `select`, `evolve`, `party-add` and `party-remove` events require Home. `release` also permits a nonactive member during a rules-10 through rules-15 wild encounter, while older carried-over encounters retain the Home-only restriction. These collection and companion mutations require no active practice duel for the same device; active practice returns **409 `partner_locked`**, while unavailable practice state fails closed. An already committed batch retry still returns its original receipt even when a practice duel is now active, without applying a companion or collection change again.

### Touch capture input

The current UI submits `{type:"ring-capture",value:phaseMs}` with an integer phase from 0 through 2399. It is an additive rules-13 event; core code derives timing quality from the phase and actual saved opponent. Green is within 12 pixels of its target radius, orange is more than 12 and at most 24, and red is farther away, using shared inclusive Q8 boundaries. The factors are green100%, orange50%, red10% of `captureChance(state)`, applied exactly once as `max(1,floor(base*factor/100))` for an eligible base; ineligible stays zero. Every accepted ring throw draws once and saves that exact percentage/result. New ring throws are calm even for an older active encounter, retaining its own base-odds formula. Three unsuccessful throws end gently. Clients supply neither grade, percentage nor result.

The historical rules-10 event `{type:"flick",value}` retains its deterministic encoding and replays identically. The earlier binary ring used41140 for an on-band hit and0 for a miss; pending events keep those historical outcomes. `value` is an integer from 0 through 82175, packed as `(dx + 160) * 256 + reach`, with integer `dx` in −160…160 and `reach` in 0…255. Coordinates use a fixed 412 × 412 logical canvas: launch `(206,300)`, landing `(206 + dx,300 − reach)`, target `(206,120)` with radius 48. Native replay decides a hit using `dx² + (180 − reach)² <= 2304`. Clients submit neither a hit flag nor a capture result.

A valid flick requires a weakened Tactical encounter or an Auto encounter awaiting a manual capture gesture, an available collection slot and fewer than three attempts. In rules-12/13 encounters, a hit makes one authoritative chance draw; an aim miss consumes one throw without drawing capture RNG. Neither a miss nor a breakout triggers a wild counterattack. The third unsuccessful throw ends the encounter gently at Home. Invalid gestures/context consume nothing; collection-full rejection remains non-consuming. Carried-over rules-10/11 encounters retain their prior counterattack and exhaustion behavior. Durable receipts bind the exact packed gesture, and retries after interruption or restart cannot reroll or add a second member.

Flick was introduced in schema 13/rules 10; its encoding is unchanged in schema 22/rules 15. Frozen rules-1 through rules-9 histories reject it. Health retains `capabilities.captureFlick:1` and `captureTimingRing:1`, and adds `captureTimingQuality:1` after startup verifies the exact native `--capture-ring-contract` probe. The current browser requires the new capability; old cores fail closed. The ring shrinks and resets on elapsed time, with its target band chosen by form. A fresh press in the main play area immediately submits one timing result. Navigation controls are excluded; release and a 450 ms guard prevent a held contact or rapid double tap from issuing another throw. Later dragging or interruption cannot undo a committed press. This browser implementation does not establish physical touchscreen accuracy.

Completed state and each collection member expose base `combat:{maxHp,attack,defense,magic,resistance,type,skills:{physical,heavy,magic}}` separately from `care:{bondRank,offenseBonus,protectionBonus,effective:{maxHp,attack,defense,magic,resistance}}`. Bond rank is `min(4,floor(bond/50))`; mood ≥80 adds one offense point, fullness ≥80 adds one protection point. Each bonus is capped at five. Offense adds to Attack/Magic; protection adds to Defense/Resistance. Care adds no permanent stat growth, maximum HP or XP; XP and existing explicit evolution level/bond routes remain authoritative. Full-mood Play consumes no energy and cannot farm bond. No offline deprivation/death is introduced. A carried-over old battle exposes zero active care bonuses until it ends, preserving its saved resolver; inactive members show their current-rule preview. Practice remains its independent frozen rules 7 system; new native Nearby matches freeze and agree their care modifiers at setup.

Rules-12 capture uses the active partner as the level reference: `HP base = 50 + floor(40 × (maxHP − 2 × HP) / maxHP)`, minus rarity penalty common/uncommon/rare = 0/10/20, minus `min(25,5 × max(0,targetLevel − partnerLevel))`, clamped to 10–90%. At half HP the chances are 50% common/same-level, 45% common/+1 level, 30% rare/same-level and 25% rare/+1 level. Current normal encounters match the partner level; the level penalty is ready for valid higher-level targets. Historical Flick accuracy remains hit/miss. Current RingCapture applies the documented timing factor to this already-adjusted eligible base, with no extra rarity, level or care factor. Care affects combat damage, not a separate capture percentage. The browser and firmware show the prospective timing-adjusted chance before a press and the exact saved chance after it; green means the full eligible odds, never100%.

Every state has `lastCapture:{sequence,targetFormId,targetLevel,chance,attempt,result}`. `result` is `none`, `miss`, `escaped` or `captured`; an unused record is all zeros with `none`, and a miss has chance zero and displays “Miss”, never a catch percentage. A captured/escaped record accepts chance1 through90; historical miss remains exactly zero. The record survives Home and reload until another throw replaces it. Historical snapshot 20 was 664 bytes; current snapshot 22 is 2,964 bytes. Older binaries such as110212b cannot read new1–9% records, so downgrades require compatible firmware or each unit’s pre-upgrade backup. New-rule Auto traces also carry each capture step's exact `{chance,attempt,result}`. Three cinematic wiggles reveal one saved outcome; they are not extra probability checks. A successful capture adds exactly one stable owned member.

Current native state also supplies `recoveryRestCount`, an integer 0–40. It is zero outside Home, when fully recovered, or when a safe bounded recovery cannot be applied. The current roster needs at most 12 ordinary Rest events. After explicit confirmation, the browser sends exactly this count of `{type:"rest",value:0}` events in one existing save-sync batch. Each Rest still restores up to 25 HP and 25 energy, adds bond only when useful, and grants no XP. There is no new recovery endpoint, free healing rule or background action; stale revisions, mixed invalid actions and uncertain responses use the ordinary rollback and exact-retry rules.

`queuedEncounters` is a native integer 0–42,949,672, and `stepsToNextEncounter` is 0–100. They describe saved step credit without inventing physical step proof. Historical `walk` harness encounters consume 100 step credit; production `explore` pacing is described below. The native selector draws from authored common/uncommon/rare tiers using 70/25/5 weights within the eligible stage/level pool; it has no pity timer or per-form guarantee. `wildRarity` is `"common"`, `"uncommon"` or `"rare"` only in a rules-10 through rules-15 encounter, and is null at Home/Egg or for a carried-over older encounter. Rarity affects encounter selection and new rules-12 capture chance; it does not change damage, XP rewards or practice selection. Catalog page entries and details expose the matching `encounterRarity` label from the authored native table; it is not an official Digimon rarity classification.

## First-run egg contract

Only newly claimed identities start at revision 0 with `phase:"egg"`, `onboarding:{completed:false,starterId:null,offerSeed:0,offers:[0,0,0]}`, no members and `activeCreatureId:0`. Care, movement and battle actions remain unavailable until hatching.

Before showing choices, the browser calls authenticated `POST /api/starter-offers` with `{}`. The service generates a nonzero cryptographic 32-bit offer seed, replays `starter-offer-seed`, and persists its event/receipt before returning. The deterministic core draws three distinct eligible level-1 Rookie forms, excluding the fixed eight. Concurrent/repeated calls and reload use that saved set, without a new draw or revision. A completed identity returns 409 `onboarding_complete`. A browser with any pending action must reconcile it before initializing offers; old bodies remain exact and receive the usual explicit migration conflict.

`GET /api/starters` still supplies the eight fixed profiles. The three saved form IDs use the bounded roster detail at level 1 for names, stats and available art; Hatch 9, 10 and 11 resolve their saved slot, never a caller-supplied form ID. Hatch creates one founder and uses ordinary revision/receipt handling. Back/review screens do not change the game. Missing art remains an honest placeholder.

Container 14 retains each identity's immutable `initialMode`: `onboarding` or `legacy`. Pure store migration never randomizes offers or hatches an egg. Existing completed identities are unchanged. Existing eggs initialize their new offer fields only through the explicit durable seed transition. No real development store was opened during these isolated tests.

## RPG progress and evolution

Completed state and each collection member include `xp`, `xpToNext` and `formId`; top-level `maxLevel` is 20. `species` identifies the current form's stable lineage; a successful cross-lineage evolution changes it to the target form's lineage. Existing saved lineage IDs/slugs are preserved during migration, while `creature`/member `name`, `stage` and combat describe the current form. The native core owns XP awards, level thresholds, stats and legal evolution edges. Care grows bond but gives no XP; only successful wild battles/captures award XP. Practice grants no XP. The same terminal event commits its reward, so retrying a captured or won result cannot grant XP twice.

Top-level `evolution:{options:[{formId,name,stage,requiredLevel,requiredBond,previewLevel,artId,eligible,combat}]}` contains at most two legal next-form previews for the selected member. `combat` is calculated natively at `previewLevel`, which can exceed the current level for a locked option. Clients display these values and send only `{type:"evolve",value:<formId>}`. They cannot set XP, level, stats or a different member's form. Native replay checks a directed edge from the current form, that edge's level/bond requirements and the home phase; the service additionally checks the active-practice lock. A rejected mixed batch applies nothing. The ordinary base revision and exact receipt bind confirmation to the authoritative history.

The compatibility evolution catalog accepts a native lineage slug validated against the generated runtime roster, retaining the original twelve lineages and their historical family anchors. Slugs contain lowercase ASCII letters, digits and single hyphen separators, at most 63 bytes. It returns one bounded historical lineage tree. Use the paged evolution graph below for current routes, including shared-parent and cross-lineage edges; historical family fields are not a complete current adjacency list. `parentId:0` identifies the root; `children` contains at most two IDs. Stages may also include Fresh, In-Training, Armor and No Level; original creatures can use null/Original. `artId:null` explicitly means no supplied artwork. Merely possessing an asset never unlocks a form.

Current state also contains `journal:{capacity:512,obtainedFormIds:[...]}` and `nextMemberId`. Journal form IDs are sorted, unique and bounded to 512; successful capture and evolution mark the obtained form. Releasing a nonactive member frees one of the 60 collection slots while preserving the lifetime capture count and journal. Member IDs increase monotonically and are never reused; selection and release use those IDs, not array positions. The founder may be released only after selecting another member. Releasing the active member, releasing during a carried-over rules-9-or-earlier encounter, or changing collection membership during active practice is rejected. During a rules-10 through rules-15 wild encounter, an explicit nonactive release frees a slot while preserving the opponent, current partner, HP, RNG, turn, attempts, cards and chosen mode. The ordinary durable receipt prevents an uncertain response from releasing another member, and an invalid mixed batch rolls back the release too. Neither mode releases companions automatically.

## Paged evolution graph

`GET /api/evolution-graph?formId=<id>&offset=0&limit=16` returns one page from the connected component containing the chosen native form. The component includes incoming and outgoing connections for browsing; legal evolution still follows only a directed outgoing edge. The route is read-only, requires no token, and applies the usual Host/Origin/peer policy. `formId` is required and must be a known ID within 1–512. Offset defaults to 0 and is bounded to 512; limit defaults to 16 and is 1–16. Query fields must be unique canonical decimal integers; extra fields are rejected.

```text
{formatVersion:2,rulesVersion:15,catalogVersion:6,focusFormId,
 offset,limit,total,nextOffset:null|number,
 forms:[{formId,name,stage,artId,minLevel,minBond,previewLevel,combat,
         parents:[formId],children:[formId],
         edges:[{toFormId,requiredLevel,requiredBond}]}]}
```

Native output and the response are bounded to 16 KiB. Rows are ordered by form ID, with at most 16 per page and 512 total forms as the protocol ceiling. Each node has at most two outgoing edges; incoming parents can be shared. The production graph contains 266 forms and 166 directed edges; ten legacy forms and six legacy edges remain only for compatibility. Edge requirements can exceed a target form's own minimum, so clients must show the edge's gates when confirming a route. The combat preview comes from native code at the node's `previewLevel`; clients supply no stats. `nextOffset:null` ends pagination, and `offset==total` returns an empty final page. An unknown form or offset beyond that component's end returns 404; malformed queries return 400. Browsing pages never mutates a companion.

Roster detail separately exposes `evolution:{parents,children,edges,status,reason}`. Status is `progression` with outgoing edges and null reason, or an explicitly documented `terminal`/`independent` leaf with a reason. It is not inferred from whether parents exist. Historical `parentId`/`children` remain intact for compatibility; use `evolution` for current progression. These are authored game paths, not a claim that every edge is an official canonical evolution.

## Bounded World DS catalog and private form art

The source catalog contains 255 independently identified game entries, while the native runtime contains 276 forms including preserved originals and forms without a corresponding source sheet. Metadata is loaded once from fixed local generated files; no request can choose a file or fetch the whole roster's artwork. Missing/corrupt metadata fails its routes without resetting saves. All metadata routes use the normal Host/Origin/peer policy and need no token; private art additionally requires the paired bearer token.

| GET route | Result and bounds |
| --- | --- |
| `/api/roster?offset=0&limit=8&q=&prefix=a&stage=Rookie` | `{formatVersion:1,catalogVersion:6,rulesVersion:15,total,offset,limit,entries}`; default limit 8, maximum 16 |
| `/api/roster?ids=1,18,67&limit=3` | At most 16 unique known native form IDs in requested order, including forms outside the 255 source entries |
| `/api/roster/<formId>?level=<level>` | `{formatVersion:1,catalogVersion:6,rulesVersion:15,form}`; default level is that form's native minimum |
| `/api/roster/art/<formId>` | Bearer required; `{formId,artId,version,sha256,packText,provenanceText}` for one verified private pair |

Search `q` is at most 64 UTF-8 bytes; `prefix` is one lowercase letter. `stage` filters the source-game stage: Fresh, In-Training, Rookie, Champion, Ultimate, Mega, Armor or No Level. Search filters compose; `ids` cannot be combined with them. Offset is 0–512, levels 1–20, and known form IDs lie within 1–512. Duplicate/unknown parameters, repeated IDs and illegal levels return 400; unknown individual forms return 404. Source browsing sorts by source display name; ID lookups preserve the requested order.

A brief entry has `{entryKey,formId,name,sourceName,stage,combatTier,role,type,previewLevel,combat,art}`. For native-only forms, `entryKey` is null. Detail adds `lineage`, native requirements, historical `parentId` and numeric `children`, current `evolution`, `baseStats`, `growth`, `statModel`, `obtainable`, `leafReason`, `skillLabelOrigin`, `source`, `official`, and `canonicalEvolutionClaim:false`. Combat values come from generated native-equivalent legal-level rows, never a JavaScript reimplementation. `statModel` distinguishes preserved rules-4 curves from authored linear growth; base/growth metadata does not replace authoritative preview combat.

`source` retains game-listed name/stage, list and sheet URLs, uploader and creator credit. `official` independently reports verified reference name/stage/type/attribute/URL, special-move labels, mapping qualification and variant-review notes. An empty official attribute means the reference did not list one. Source stages, official taxonomy and authored four-element battle types remain separate. Current combat skills include reviewed official bindings in selected Physical, Heavy or Magic slots; other slots retain authored labels. The two updated original Ultimates report `role:"Original"` and `statModel:"original-ultimate-v9"`; the underlying preservation flag identifies their existing form identity, not unchanged stats. Detail reports `skillLabelOrigin:"mixed-reviewed-official-and-authored"` for the 26 affected forms. The reviewed binding table records source and semantic basis; it does not import upstream damage, status effects or numerical profiles. Curated game evolution edges do not claim official canonical paths. The round Field notes carousel shows bounded verified labels as “Encyclopedia move”, names the referenced identity and retains any sheet-identity review qualification; References opens the official page. This reference carousel is separate from the effective three combat moves returned in `combat.skills`. Tactical choices and recorded Auto traces use those native labels, with the category still visible; historical traces retain their original labels.

An art descriptor is `{status:"private-local-available"|"unavailable",artId,version?,url?}`. The current local index explicitly approves only installed form packs; absent art stays unavailable and does not remove a playable form. The private route verifies fixed index entries, confined immutable paths, byte counts and SHA-256 before returning one pack/provenance pair. No raw source, filesystem path, audit notes, arbitrary filename or directory route is exposed. Absent art returns 404; corrupt art returns 503 and the client retains its existing appearance. Limits are 256 KiB pack plus 64 KiB provenance, a 1 MiB/512-entry local index, and 64 KiB metadata responses. The scene-only production device catalog is separate from this private art index; it is not a bulk 255-form art endpoint.


## Walking encounters (schema 22, rules 15)

`{type:"encounter-seed",value:1..4294967295}` initializes the independent saved pacing RNG once, after starter selection and before any pacing target exists. Native firmware supplies a hardware random value and checkpoints it before accepting exploration; retries cannot redraw it. This value is replay input, not a security credential or evidence of real movement. The host core retains a deterministic fallback when a test omits this event.

`{type:"accrue-steps",value:1..1000}` accounts for valid walking after starter selection, including menus and an ongoing wild/Nearby/practice battle. Crossing the unchanged randomized threshold saves one `walking.pendingEncounter:{formId,level,rules}` without changing the current fight or screen. Further walking updates eligible steps but cannot reroll that result, advance its next threshold or build a queue while the slot is full. The native pedometer separately owns lifetime physical steps; the service does not infer that total or collect GPS routes.

`{type:"present-encounter",value:0}` consumes that slot only while the game phase is Home. Firmware issues it on a quiet Home screen after the current interaction, menu or match finishes. The service also defers it during an active practice match. Restart and batch retries retain the selected form and level. Off explicitly stops new accrual; it does not erase an already earned encounter.

Historical `{type:"explore",value:1..1000}` remains replayable with its original Home-only immediate encounter behavior. It rejects Egg, an active encounter, Off and an occupied deferred slot. The existing browser walk demo continues to use this immediate harness action; the actual device controls deferred presentation.

`{type:"encounter-rate",value:0..3}` saves Off, Relaxed, Normal or Frequent while Home. It preserves the already decided target and RNG. The randomized first interval is 80–160 effort points; subsequent intervals are 160–280. One eligible step advances 1, 2 or 3 points at Relaxed, Normal or Frequent. Normal therefore averages about 60 steps for the first encounter and 110 thereafter. Off pauses progress. No setting changes rarity, rewards or progression requirements. The current schema exposes `walking:{rate,name,eligibleSteps,encounters,rngState,target,progress,remainingSteps,pendingEncounter}`; `remainingSteps` is zero before initialization, during Egg, when Off or while the one slot is occupied, otherwise it reflects the saved threshold even during an active fight. Its RNG is separate from capture RNG.

The historical `walk` action remains for replay and test injection. It is not a production pedometer event. A single sync batch containing an invalid action rolls back all its exploration, seeding and result changes.

## Wild battle modes and recorded traces

Completed saves include `battleMode:"tactical"|"auto"`, numeric `autoCapture` (0 for none, 1 for awaiting a flick), and `lastAutoBattle:null|{sequence,turns,outcome}`. Save `{type:"mode",value:0|1}` at Home to choose the next encounter's mode. Choosing Auto or walking does not resolve a battle.

The current UI sends `{type:"auto-fight",value:0}` after confirmation. The bounded native policy chooses Physical or Magic for each attack and completes the exchange that first makes capture eligible. It then saves an Encounter state with `autoCapture:1` and a nonterminal trace. No capture attempt or capture RNG draw occurs. Playback completes before the capture screen accepts a gesture. The additive `{type:"ring-capture",value:phaseMs}` and historical `{type:"flick",value}` events are accepted in this paused Auto state; the current UI and its buttons submit ring-capture. Failed throws retain the pause until the third miss or breakout ends the encounter gently. The graded timing factors apply to the existing eligible odds; the three-throw limit and capture cinematics are retained.

Choosing Resume fighting sends `{type:"auto-resume",value:0}`. It resolves attacks through the end of that encounter without another capture prompt. Each command advances the outer sequence once; each trace contains at most 48 turns. Invalid batches persist no partial result. Exact retries recover the same state and trace without duplicate rewards. Pause state survives restart and background step accrual.

Historical `{type:"auto",value:0}` retains its original automatic capture policy for exact rules 13 replay and compatibility with old clients; the current native and browser UI do not send it. Practice and Nearby PvP retain their existing behavior. See [manual Auto capture](../docs/AUTO_CAPTURE.md).

Pairing, save reads and successful sync responses include top-level `autoTrace`, which is null until a reconstructable Auto result exists. This is native replay data for presentation, not a sequence of commands the browser should send. Its shape is:

```text
{formatVersion:1, mode:"auto", kind:"wild"|"practice",
 startSequence, endSequence, outcome:"none"|"won"|"captured"|"retreated"|"lost"|"draw",
 player:{species,name,level,combat,formId?}, enemy:{species,name,level,combat,formId?},
 steps:[{turn,phase:"attack"|"defend",action,opponentAction,
         playerHpBefore,playerHpAfter,enemyHpBefore,enemyHpAfter,
         reflected,captured,guard?}]}
```

`action` is `physical`, `heavy`, `magic`, `capture`, `brace`, `counter` or `ward`; `opponentAction` is null or one of those move names. New native traces may include participant `formId` and a step `guard` of null, brace, ward or counter; historical traces retain their exact older shape. Wild rules 12/13 traces additionally have `combatRulesVersion:12`, `playerCare` and `enemyCare` each `{offenseBonus,protectionBonus}`, plus `{chance,attempt,result}` on capture steps. Participant combat remains the base profile, with care kept separate. Turns are numbered from one. Wild traces contain at most 48 steps, practice traces at most 40 for rules 5–7 and 30 for rules 2–4. Participant names, species, levels and combat profiles are captured before resolution and remain correct after capture, partner changes or training. Frames describe combat HP before terminal care/reward handling; gentle retreat or a level increase can make final save HP differ from the last frame. Private RNG, unrevealed intentions and snapshots are excluded from traces.

A wild trace with outcome `none` is an attack-only capture pause: both final HP values are positive and match the saved Encounter. It remains across background step accrual and is cleared by a later foreground action such as a flick. Practice traces cannot use `none`.

The latest terminal wild summary and trace remain available after later care or mode changes and are replaced by the next Auto result. An exact receipt retry reconstructs the trace at that receipt's event boundary. Reload/GET and animation playback never submit a new Auto action. The browser treats a result as newly pending presentation only when its sequence matches the saved action, rather than automatically reopening historical playback. Native trace output is bounded to 16 KiB; the browser practice client accepts at most 32 KiB per response.

## Retry and conflict contract

Each nonempty batch contains 1–100 events. Clients generate an 8–80 character `[A-Za-z0-9_-]` batch ID and durably retain the exact batch and its base revision before sending. For current rules-15 batches, the same ID and semantic body always return its original result, even after later batches or server restart. `rulesVersion:15` is part of the idempotency checksum. Object key order is irrelevant. Reusing an ID for different content returns `409 batch_mismatch`. A new batch based on an old revision returns `409 revision_conflict`. Fetch `/api/save` and explicitly reconcile; do not silently overwrite or automatically replay local progress onto another device's changed history.

The service stores accepted events and an optional migrated baseline, then computes state by invoking the **same C++ deterministic rules core** used by host and firmware. Clients cannot upload arbitrary health, inventory, captures or levels. The game demo seed is fixed at 12345, while starter offers use an independent per-device seed; this is not suitable for competitive rewards. Server-side replay validates rules and progression, but cannot establish the truth of client sensor readings. The native core requires no network. This browser prototype calls the loopback service for each action; full offline browser play is not implemented.

## Separate practice battle contract

Tactical practice actions are `physical`, `heavy`, `magic`, `brace`, `counter`, `ward`, `retreat` with value 0, or `card` with value 1 or 2. The native core checks the current attack/defend phase. The optional `mode` field is accepted only on start; omission selects Tactical and preserves the old request shape. An explicitly supplied value must be `"tactical"` or `"auto"`. Auto start resolves the whole duel immediately after confirmation and returns a durable terminal battle plus its trace; there is no second action required. New manual actions against that result return **409 `battle_auto_complete`**, and active Tactical duels cannot change mode or be replaced by another start. Request IDs use 16–64 characters from `[A-Za-z0-9_-]`; revisions are nonnegative integers. Inputs must have exactly the documented fields. Companion identity, level and form are read from the authenticated device's current care save at start, never from the request body.

New practice state is schema 7/rules 7, with `maxExchanges:40`, at most 40 resolved exchanges and sequence at most 42. Rules-5 and rules-6 duels also retain their 40-exchange limit; rules 2–4 retain their 30-exchange limit and omit `maxExchanges`. Public state includes `playerFormId`, `enemyFormId`, `playerFormName` and `enemyFormName` alongside the existing species, combat, HP, hint and exchange fields. Species remains lineage; the form supplies name/stats. The trusted companion has `{id,species,name,level,formId}` with level 1–20. Each new duel asks the native stage/level-eligible roster selector for a rival at the selected companion's current level. The service validates the selected companion's form, lineage, name and legal level against generated runtime metadata before native battle creation; no client supplies those values. A new random 32-bit seed is generated at start; subsequent commands restore its saved RNG. Both sides begin at their own maximum HP; care HP and other care values do not enter practice.

Practice rules 6 introduced a minimum raw attack damage of `max(4, ceil(intendedDefenderMaxHp / 20))` before type and guard modifiers. Rules 7 retain that floor with its new bounded Auto policy. The floor applies only to practice duels and does not change profile stats, maximum HP, move labels, wild battles or care rewards. Tactical and Auto use the same native resolver.

Existing schema/rules-2 through -6 duels keep their frozen resolvers, profiles and public shapes. Rules-2 companions remain `{id,species,name,level}`; rules-3 retains its form fields and original 66-form bounds. They are not rerolled or converted to new combat values. Actions use the saved duel's marker, 2 through 7. A mismatched action marker returns **409 `battle_migration_required`**. New starts require 7, but an exact retained old start/act receipt using 2 through 6 still returns its original result before new-start or current-duel guards. An uncommitted old start requires explicit reconciliation, never automatic relabeling. Adding a current marker to a committed old request changes its hash and produces **409 `request_mismatch`**.


All practice success responses have `{revision,battle,mode,autoTrace}`. Tactical responses have `autoTrace:null`; Auto responses contain the native recorded trace. Private snapshot bytes, RNG and unrevealed move choices never appear in HTTP output. Practice has its own revision counter and mirrored `battle-store.json`, bounded to eight devices, 32 success receipts across supported rules and at most 32 reserved legacy request IDs per device. Exact current-rule retries return the original result, including mode and trace, even after another duel; mismatched IDs and stale revisions fail. Lookup of a retained receipt precedes current-duel mode/status guards. Supplied start mode participates in the request checksum; an omitted mode is not inserted into that checksum, preserving old pending bodies and stored hashes. Adding or changing mode on a reused request ID produces **409 `request_mismatch`**. Active practice cannot be replaced by another start. The separate module initializes lazily, so broken practice data does not prevent pet-save recovery. Both stores share the existing exclusive writer lock. The current duel's terminal status is durable; there is no cumulative win/loss record.

The current practice container is format 8. Each current record and retained receipt stores its mode and a native snapshot whose validated header chooses rules 2 (112 bytes), rules 3 through 7 (120 bytes). Auto records additionally retain their original starting snapshot of the same format. The service regenerates the bounded trace with that snapshot's native resolver and verifies that terminal bytes match the committed snapshot. GET/retry does not select a new seed and large traces are not duplicated in stored receipts. Known format-3 through format-7 stores are archived as `battle-store.format-v<oldFormat>.json`; their devices, snapshots, profiles, modes, receipt bodies/hashes and revisions remain unchanged. The new container is bounded to 1 MiB per copy.

Existing snapshots, companion profiles, revisions, receipt IDs and body hashes remain unchanged. Old requests without mode remain valid exact retries; they must not be relabeled by adding a mode field. Unknown future containers fail closed.

On first load, a known format-1 practice store is archived as `battle-store.rules-v1.json`. Only its current duel migrates: native code preserves RNG, committed move, hints, prior outcomes, status, exchanges and card state; HP scales upward proportionally with `ceil(oldHp × newMaxHp / 100)` and zero remains zero. The old rival becomes level-1 Flicker under the explicitly changed rules. Companion identity and revision remain unchanged; the migrated snapshot remains frozen rules 2 and 112 bytes. Old receipt IDs remain reserved, while the new-rule receipt list starts empty. Practice commands do not mutate the ordinary pet save and have no rewards or penalties. Unknown/corrupt pending commands are retained by the browser. [Rules and platform limits](../docs/PRACTICE_BATTLE.md).

## Storage, limits and recovery

The ignored `.data` directory holds the store, mirror and writer lock. Random 256-bit bearer tokens are returned once; only SHA-256 token hashes are stored. Files are created with mode 0600 and new directories with 0700. The local browser stores its development token; browser profile access is equivalent to device access. This is development identity, not a production enrollment design.

A single synchronous commit writes and fsyncs a same-directory temporary file, atomically renames it, and fsyncs the directory. Both mirror and primary contain each acknowledged save. A corrupt or missing primary is restored from a structurally validated mirror. An interrupted commit can leave a batch present without the client receiving its response; retrying its retained batch ID is safe. Batch checksums, bounds, strict versions and replay validate loaded history. Invalid stores without a valid mirror fail startup. Known legacy stores follow the explicit migrations above. All other unsupported versions fail closed and require an explicit migration; they are never silently reset or rolled back.

Only one writer may open a save directory. A second process fails startup. Clean shutdown removes `.data/.writer.lock`. After a crash, stop all service processes, inspect the lock's PID, back up `.data`, and only then manually remove the stale lock. Never remove the lock while a writer is running.

Resource limits include a 64 KiB state JSON buffer (measured worst-case 38,430 bytes), 32 KiB per request, 100 events per batch, 10,000 lifetime events per device (legacy plus current events), eight devices, 16 MiB per care-store copy, 1 MiB per practice-store copy, 32 connections, and a three-second core replay timeout. All care batch receipts remain until the lifetime limit; ancient retries cannot reapply discarded batches. At the limit, the prototype refuses new progress rather than truncating history. A future checkpoint/migration format must retain its retry boundary before this limit is increased. Pairing starts are capped at 30 per minute with 32 outstanding codes. Codes live only in process memory and expire on restart. Signed browser packs are limited to 256 KiB, native device blobs to 128 KiB; the older starter compatibility fixture has a separate 512 KiB read cap.

No raw GPS routes, location coordinates, names, age or child profile data are accepted. Battery state and charging control are not claimed by this service.

## Signed asset packs (implemented in the local prototype)

`GET /api/assets/catalog` returns `{keyId, payloadBase64, signature}`. The exact decoded UTF-8 payload is signed with P-256/SHA-256, encoded as a 64-byte IEEE-P1363 signature. The client pins the public SPKI key in its application source. **The committed RFC 6979 key is public test data and provides no production publisher authentication.** Production mode is refused; an owner-controlled signing key, pinned firmware public key and verified HTTPS transport are future release work.

The catalog’s `rulesVersion:1` is its asset-binding compatibility epoch, independent of game rules 15; changing gameplay does not re-sign unchanged art. Decoded payload: `{formatVersion:1, release, rulesVersion:1, packs:[{id, version, bytes, sha256, url, required,decodedBytes}]}`. `decodedBytes` is the sum of sprite frames expanded to browser RGBA, or 921,600 for one 480 × 480 background; it is a validation bound, not resident memory. Download paths are fixed to `/api/assets/packs/<id>/<version>` and startup rejects altered pack bytes, unsupported schemas or a bad catalog signature.

A full-content development installation can expose eight optional format-3 scene packs, `scene-{meadow,forest,beach,ruins,cavern,snow,volcanic,digital}-v1`, using the same signed manifest fields and endpoints. This source publication omits those private scene payloads and its normal catalogs are empty; the original sprite fixtures are opt-in only. Each background pack carries its identity, version, rules epoch, license text, source PNG hash and one canonical-base64 baseline JPEG with dimensions exactly 480 × 480; it has no sprite fields. The source license remains explicitly unspecified. [Exact pack and cache contract](../docs/ASSET_CACHE.md).

`GET` / `HEAD` pack routes return strong ETags and immutable versioned content. A single `Range: bytes=start-end` request returns `206` with exact `Content-Range`. Matching `If-Range` resumes; a stale value returns complete `200` bytes which the client replaces, never appends. Invalid/multiple ranges return `416`. `If-None-Match` supports `304`. Downloads require no bearer token but retain the prototype's loopback and origin checks. No Wi-Fi credential or GPS location is part of an asset request.

Browser bounds remain 256 KiB encoded per pack, 16 KiB requested chunks and 1 MiB accounted cache. Format-1 sprites use 16/32-square pixels, sixteen RGB565 palette entries, at most eight frames per animation and at most 2 MiB all-frame RGBA cost per pack. Format-3 JPEGs are at most 150 KiB before base64 and undergo strict header/size validation before image decode. Hash verification precedes JSON parsing; manifest verification precedes trusting its paths or sizes. The existing schema-1 cache adds optional `backgroundActive` alongside sprite `active`; old records without it remain valid. Staging protects the prior verified scene; activation updates only the scene pointer and its anti-rollback boundary while preserving the active sprites. Game saves remain separate. See [cache implementation and caveats](../docs/ASSET_CACHE.md).

The older `/api/catalog` returns no creature packs in normal mode and `/api/packs/starter-v1` returns 404. Explicit development fixture mode enables these compatibility endpoints. The simulator uses signed `/api/assets/*` scenes and named placeholders when private creature artwork is unavailable; it bundles no toy creature fallback.

## Native device asset protocol

The separate device profile is `s3-146-v1` for the Waveshare ESP32-S3-Touch-LCD-1.46, with native 412 × 412 backgrounds. It preserves the browser's existing packs and routes. These read-only routes need no bearer token but always pass the configured Host, Origin and socket-peer policy:

| Route | Contract |
| --- | --- |
| `GET /api/device/health` | Exactly `{status:"ok",protocolVersion:1,gameRulesVersion:15,gameSchemaVersion:22,assetProfile:"s3-146-v1"}`; no query parameters |
| `GET /api/device/assets/catalog` | Development signed envelope `{keyId,payloadBase64,signature}`, at most 8 KiB |
| `GET` / `HEAD /api/device/assets/packs/<id>/<version>` | Raw DVA1 sprite or baseline JPEG bytes; no JSON/base64 wrapper |

Health confirms that the configured service answered with compatible protocol/game versions. It does not assert internet reachability, successful Wi-Fi association, available asset files, or synced progression. Missing/corrupt native assets return **503 `device_assets_unavailable`** from their routes while health, care saves and browser art remain usable.

The decoded catalog payload is at most 6 KiB: `{formatVersion:1,release,rulesVersion:1,profile:"s3-146-v1",packs:[{id,version,bytes,sha256,kind,width,height,url}]}`. The asset rules epoch remains separate from gameplay rules 15. The protocol ceiling is 24 entries; normal full-content mode exposes the eight `scene-<scene>-412-v1` packs (412 × 412) from the fixed index. This reduced publication serves an empty signed catalog because those scenes are omitted. The service-side empty-manifest allowance is a documented export adaptation; native171cda7 code remains unchanged. The ten original sprite fixture packs are hidden. No request can select a local filename, raw source, private pack or arbitrary URL.

Every blob is at most 128 KiB. Startup confines filenames, rejects symlinks, checks SHA-256/length against the generated index, and validates format before caching immutable response bytes. DVA1 sprites additionally require their 32-byte little-endian header, version/dimensions, six bounded animation records, 17 packed frames and payload CRC32. JPEGs require a bounded single baseline scan with dimensions exactly 412 × 412. The same public RFC 6979 P-256 fixture signs exact UTF-8 manifest bytes with SHA-256 and a 64-byte IEEE-P1363 signature. It provides **development interoperability only, not production publisher authentication**. The envelope is created in memory at service startup; its signature/ETag may change after restart while unchanged pack hashes/ETags stay stable. Blob content changes require a new asset version and release.

Device requests use ordinary single-byte ranges, including **4 KiB chunks**. Strong ETag equals the quoted blob SHA-256; matching `If-Range` yields `206`, stale `If-Range` yields a complete `200`, invalid/multiple ranges yield `416`, and `If-None-Match` can yield `304`. The client must verify status, declared lengths/range and final hash; JSON error bodies are never assets. The service emits no redirect. Browser 16 KiB download behavior is unchanged.

## Explicit LAN development configuration

Default startup reads no LAN setting unless `DIGIVICE_LAN_BIND` is provided. It must be one exact RFC 1918 IPv4 interface address (`10/8`, `172.16/12`, or `192.168/16`). Wildcard `0.0.0.0`, public addresses, hostnames and IPv6 binds are rejected. No interface is discovered or enabled automatically.

| Setting | Meaning |
| --- | --- |
| `DIGIVICE_LAN_BIND` | Explicit private interface address; the single HTTP listener binds there instead of loopback |
| `DIGIVICE_LAN_HOSTS` | Optional comma-separated exact HTTP authorities, including port; defaults to the bound IP, `127.0.0.1` and `localhost` at `PORT` |
| `DIGIVICE_LAN_ORIGINS` | Optional comma-separated exact `http://` origins drawn from the Host allowlist; defaults to those origins |

Allowlists contain at most eight entries. Allowed hosts must be the bound address, loopback or an explicitly named `.local` host; the bound address must be included. Actual socket peers must be loopback or RFC 1918 IPv4. Forwarded headers cannot change that identity, and cross-site fetch requests remain refused. This is unencrypted development HTTP on a trusted local network, with unchanged bearer-token protection for saves, practice, private form art and Garage. It does not enable production mode, TLS, internet routing or cloud/Pi replication.

**Pair before switching modes.** Pairing start and claim always require an actual loopback peer in LAN mode; a remote LAN peer receives **403 `local_enrollment_only`**, even if it supplies loopback forwarding headers. The single LAN listener does not also listen on `127.0.0.1`. Create the development identity while running in default loopback mode, retain its existing token securely, then stop and explicitly restart in LAN mode. Return to loopback mode for further enrollment. No identity or network credential is generated by setting these variables.

Source-level LAN checks were exercised with synthetic request peers; actual HTTP tests listened only on loopback. A two-device Wi-Fi bench test and network enrollment remain separate verification gates.

## Independent world initialization (introduced in schema 20, rules 13)

Local tests may supply the explicit in-process `seedSource` dependency. ## XP companions (schema 22, rules 15)

Current state includes `partyCapacity:3` and `partyMemberIds:[...]`, an ordered list of zero through three distinct owned instance IDs. These are three additional companions beyond the active partner. They do not take extra collection slots, attack, absorb damage or alter battle odds. Old profiles migrate with an empty list; no member is selected automatically.

At Home, send `{type:"party-add",value:<memberId>}` or `{type:"party-remove",value:<memberId>}` through the ordinary rules 15 save-sync batch. IDs must be integers from 1 through 4,294,967,294. The native core rejects unowned IDs, active-partner additions, duplicates, a fourth addition and removal of an unselected ID. New edits are also blocked while practice is active. Invalid mixed batches commit nothing.
