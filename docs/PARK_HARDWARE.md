# Park hardware: verified facts and bring-up gates

Audit: **2026-10-06**. Primary target: **Waveshare ESP32-S3-Touch-LCD-1.46, standard glass, SKU 29565**. The owned **Heltec WiFi LoRa 32 V4 + L76** is an interim test platform; its exact revision remains unknown. Neither board was opened, flashed, or electrically tested during this audit. The older 2.1-inch pin map is historical and must not be used for this target.

Movement and nearby-player choices remain under discussion. Local step-triggered encounters need no GPS, phone, or network. A phone location bridge is a deferred extension, useful for place-specific events rather than a requirement for random encounters. No separate GNSS purchase is proposed. Cache, offline play and bounded networking can proceed independently.

[board_profiles.hpp](../firmware/main/board_profiles.hpp) now encodes these facts as three compile-time profiles: generic serial, Waveshare 1.46 and unverified Heltec. It contains no driver initialization. Both active button assignments remain `-1`; candidate pins do not enable controls. The header passes a C++17 host syntax/constexpr check with warnings treated as errors. That check alone is not an ESP target build or hardware test; see [ESP build evidence](ESP_BUILD.md) for the separately authorized SDK installation and cross-compilation.

## Primary board

The native screen is **412 × 412**, not 480 × 480. It uses an SPD2010 display/touch solution, an ESP32-S3R8, **16 MB flash and 8 MB PSRAM**, microSD, QMI8658 motion sensing, PCF85063 RTC, PCM5101 audio DAC, microphone and speaker circuitry. The advertised panel capability is 16.7 million colors; the inspected vendor display path uses **16-bit RGB565**, which represents 65,536 colors. No measured frame rate or battery runtime is available. [Waveshare overview](https://docs.waveshare.com/ESP32-S3-Touch-LCD-1.46)

The source of pin truth is the [official schematic](https://files.waveshare.com/wiki/ESP32-S3-Touch-LCD-1.46/ESP32-S3-Touch-LCD-1.46.pdf), checked against the [vendor source at commit fda89ff2ff32eb1bce561901225c6a36fa684237](https://github.com/waveshareteam/ESP32-S3-Touch-LCD-1.46/tree/fda89ff2ff32eb1bce561901225c6a36fa684237). That commit is dated **2026-04-30**. The schematic has no visible revision identifier; its PDF creation metadata is 2024-10-16 UTC, which is not proof of a manufactured board revision.

J9 is a **2 × 10, 1.27 mm** header exposing GPIO12/13, GPIO1/3/0, UART, I2C, SD signals, USB and power. **GPIO12/13 are candidates for two external buttons**, pending confirmation of the purchased board/header orientation and wiring; they remain disabled by default. Avoid using GPIO0/3 as ordinary button candidates because of boot strapping. The onboard PWR and BOOT buttons have power/boot responsibilities and are not equivalent to two independent game buttons. Do not repurpose shared SD, USB, display or I2C signals.

## Battery, power and storage

The schematic shows an **ETA6098** charging circuit, MOSFET power switching, an MP1605 regulator, and a divided battery measurement into GPIO8. This is not an assumed I2C PMU. Vendor documentation calls for a **3.7 V lithium battery with MX1.25 connector**; the schematic labels J1 PH1.25 2P. Confirm physical connector fit, polarity, battery protection and charging compatibility on the actual board. Capacity, charging current suitability and runtime have not been established. [Schematic](https://files.waveshare.com/wiki/ESP32-S3-Touch-LCD-1.46/ESP32-S3-Touch-LCD-1.46.pdf), [battery and power FAQ](https://docs.waveshare.com/ESP32-S3-Touch-LCD-1.46/FAQ)

The [vendor power routine](https://github.com/waveshareteam/ESP32-S3-Touch-LCD-1.46/blob/fda89ff2ff32eb1bce561901225c6a36fa684237/example/ESP-IDF-5.3.2/ESP32-S3-Touch-LCD-1.46-Test/main/PWR_Key/PWR_Key.c) configures GPIO6 input and GPIO7 output, drives 7 low, waits **100 FreeRTOS ticks**, then drives it high if PWR is still held low. Shutdown drives 7 low. Our explicitly selected 1.46 profile instead asserts the verified hold signal promptly before optional initialization. The [power controller](POWER_CONTROL.md) adds a three-second hold, cancellation, save/worker barriers and release-before-cut, with quiet standby if the CPU remains powered. These are implemented source sequences, not bench-tested behavior. USB independently supplies VCC; no verified VBUS-sense input is available. Test battery-only and USB boots, release timing, failed initialization and deliberate shutdown before relying on it. Save completion must precede an intentional power cut.

**The available microSD card is now the primary asset store.** Keep flash-resident fallback content usable when the card is missing, corrupt or unavailable; save state remains separate from downloaded assets. The board FAQ supports operation without a card and recommends FAT32 when troubleshooting, but establishes no maximum supported capacity. This choice does not imply the card has been mounted or tested on hardware. [Waveshare card guidance](https://docs.waveshare.com/ESP32-S3-Touch-LCD-1.46/FAQ)

The pinned vendor demo initializes power, I2C and the expander before mounting **one-bit SDMMC**, despite its misleading “SPI” log. Use `SDMMC_HOST_DEFAULT()` with the normal 20 MHz maximum, `SDMMC_SLOT_CONFIG_DEFAULT()`, `width=1`, CLK14, CMD17 and D0=16. D1/D2/D3 and card-detect/write-protect remain `GPIO_NUM_NC`; physical D3 is held high separately through the expander. Do not use the unused `CONFIG_SD_Card_D3=21` constant: GPIO21 is LCD CS. The schematic supplies 10 kΩ pull-ups on CMD, D0–D3 and CLK. Retaining the vendor's `SDMMC_SLOT_FLAG_INTERNAL_PULLUP` is consistent with its configuration, but internal pull-ups alone do not meet the documented requirement. [Vendor mount routine](https://github.com/waveshareteam/ESP32-S3-Touch-LCD-1.46/blob/fda89ff2ff32eb1bce561901225c6a36fa684237/example/ESP-IDF-5.3.2/ESP32-S3-Touch-LCD-1.46-Test/main/SD_Card/SD_MMC.c#L50-L94), [IDF 5.3.6 SDMMC](https://docs.espressif.com/projects/esp-idf/en/v5.3.6/esp32s3/api-reference/peripherals/sdmmc_host.html), [pull-up requirements](https://docs.espressif.com/projects/esp-idf/en/v5.3.6/esp32s3/api-reference/peripherals/sd_pullup_requirements.html)

**EXIO3 is TCA9554 port P2: bit 2, mask `0x04`, at seven-bit I2C address `0x20`.** It is not GPIO3 or bit 3. The smallest board initialization is:

1. Establish power hold and the single shared I2C bus on SCL10/SDA11. Create that bus when SD or motion needs it, including when motion is disabled.
2. Under the shared I2C mutex, read output register `0x01`, then write `old_output | 0x04`. This preloads SD D3 high before enabling its output.
3. Read configuration register `0x03`, then write `old_config & ~0x04`; a configuration bit of zero means output. Preserve every other output and direction bit, then read back both registers and require the expected values.
4. Release the mutex and mount only if every bounded I2C operation succeeded. Keep D3 high during one-bit SD operation; it is not a per-transfer SPI chip-select. Failure leaves fallback content available.

The output register reads the latch; input register `0x00` is unnecessary here and reading it can clear an expander interrupt. Leave polarity register `0x02` unchanged. Power-on defaults are output `0xFF`, configuration `0xFF` and polarity `0x00`; an ESP-only reset does not guarantee an expander power-on reset. The vendor writes configuration `0x00` for all eight ports and relies on the high output defaults. Do not copy that global direction change, its unchecked I2C results, or its `Mode_EXIO` helper, which ignores its requested direction argument. [Vendor expander source](https://github.com/waveshareteam/ESP32-S3-Touch-LCD-1.46/blob/fda89ff2ff32eb1bce561901225c6a36fa684237/example/ESP-IDF-5.3.2/ESP32-S3-Touch-LCD-1.46-Test/main/EXIO/TCA9554PWR.c), [TI TCA9554 Rev E, register map and reset behavior](https://www.ti.com/lit/ds/symlink/tca9554.pdf)

Use one board-level I2C lock for expander, QMI and later touch/RTC operations, holding it through the complete expander read-modify-write sequence. ESP-IDF 5.3.6 documents only its I2C factory APIs as thread-safe; other public operations require application serialization. Do not mix the vendor's legacy I2C driver with the project's new master-bus driver. [IDF I2C driver contract](https://docs.espressif.com/projects/esp-idf/en/v5.3.6/esp32s3/api-reference/peripherals/i2c.html#thread-safety)

Set **`format_if_mount_failed=false`**, unlike the vendor's `true`, and bound `max_files`. A failed mount must never partition or format the user's card. Use a single mount owner and orderly `esp_vfs_fat_sdcard_unmount` teardown. Keep old validated asset generations while staging replacements; flush/`fsync` success and a FAT rename are not proof that sudden power loss cannot corrupt a card or its metadata. Validate generations at boot, ignore incomplete downloads, retain the fallback and test unplug/power-cut recovery on the physical card before making durability claims. SDMMC transaction buffers also have DMA/alignment requirements; measure the actual FAT/driver buffering and internal heap rather than assuming arbitrary PSRAM pointers are suitable. [IDF FAT mount and formatting behavior](https://docs.espressif.com/projects/esp-idf/en/v5.3.6/esp32s3/api-reference/storage/fatfs.html), [SDMMC DMA constraints](https://docs.espressif.com/projects/esp-idf/en/v5.3.6/esp32s3/api-reference/peripherals/sdmmc_host.html#_CPPv425sdmmc_host_do_transactioniP15sdmmc_command_t)

## Movement and nearby players

The [QST QMI8658C Rev A datasheet](https://www.qstcorp.com/upload/pdf/202210/13-52-27%20QMI8658C%20Datasheet%20Rev%20A%20%281%29.pdf), §§11–12, documents a hardware pedometer and wake-on-motion. The step counter is **24-bit**, in registers 0x5A–0x5C, wraps after 0xFFFFFF, and can update in batches. It needs configuration, an enabled accelerometer and Non-SyncSample mode. Reset, power loss or a rising pedometer-enable bit clears it. Thus a durable total must consume bounded deltas and explicitly rebase after sensor resets; it cannot treat each read as new steps.

The vendor motion driver currently demonstrates raw acceleration, not a ready-made walking API. Verify WHO_AM_I, revision and command completion on the actual sensor. The QST document also has a parameter-bank bit-label ambiguity; resolve it before enabling a physical configuration driver. Wake-on-motion is a separate mode, and IMU interrupts reach the expander: a usable deep-sleep wake route has not been demonstrated. Handheld, pocket, clipped and shaking behavior still need measured walking tests. A software classifier or host fixture is not proof of real step accuracy.

For later nearby-player discovery, **BLE advertising plus bounded scanning** is the simplest candidate. Advertise a short-lived game session identifier, show discovered devices, and require confirmation on both devices before a challenge. RSSI can support rough presence filtering; it is not an exact distance or identity check. No GPS or internet is inherently needed for this design, and no multiplayer transport is claimed implemented here.

ESP32-S3 shares one 2.4 GHz radio between Wi-Fi and BLE. ESP-IDF 5.3.2 documents STA + BLE scan/advertising support using time sharing; SoftAP connected cases have weaker performance guarantees. Enable software coexistence and measure discovery while syncing assets, playing sound and drawing. Prefer short discovery windows and defer large downloads during a challenge. [Espressif coexistence guide](https://docs.espressif.com/projects/esp-idf/en/v5.3.2/esp32s3/api-guides/coexist.html)

ESP-NOW remains an alternative for an ESP-only link, but peers must agree on a Wi-Fi channel; joining a hotspot complicates that coordination. It also needs application acknowledgements, sequence handling and retransmission rather than assuming radio send success means the game accepted a move. That is additional work before it improves this MVP. [Espressif ESP-NOW guide](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/network/esp_now.html)

## NFC and deferred location

The candidate [ELECHOUSE PN5321 MINI, hardware V2, manual Rev 1.5, September 2026](https://www.elechouse.com/wp-content/uploads/2024/07/Elechouse-Pn5321-Mini-Product-Manual-V1.pdf) uses 3.3 V host logic, accepts 3.3–5 V supply, and offers I2C address **0x24**. This does not conflict with the listed onboard addresses. Select its I2C pads while unpowered, use common ground, and inspect aggregate pull-ups. A serialized bus driver needs bounded PN532 waits so it cannot stall touch or motion reads. Reset/power control wiring, antenna placement and actual swipe dwell remain open. A card UID identifies a card; it does not prove authenticity or swipe direction.

Location remains deferred while the user weighs its gameplay benefits. The proposed phone path, if later chosen, is Core Location → BLE → two devices sharing a group position; hotspot internet is a separate function. It would need permissions, age/accuracy checks, disconnected fallback and no raw route upload by default. It is not required for motion encounters or BLE presence.

Historical GNSS findings are retained only to prevent incompatible assumptions: the owned Heltec module is described as L76/L76K, but the exact hardware must be identified. The actual [L76K hardware manual V1.1, 2021-08-23](https://resource.heltec.cn/download/Heltec%20Capsule%20Sensor%20V3/Quectel_L76K_V1.1-1.pdf) specifies **2.7–3.4 V, typical 3.3 V**, default 9600 baud and 1 Hz, up to 5 Hz. Its [protocol V1.1, 2021-12-16](https://raw.githubusercontent.com/Seeed-Projects/Seeed_L76K-GNSS_for_XIAO/fb74b715224e0ac153c3884e578ee8e024ed8946/docs/Quectel_L76K_GNSS_Protocol_Specification_V1.1.pdf) uses CASIC/PCAS commands. Heltec's product links instead lead to an older 2015 L76 presentation with different limits: do not apply those to L76K. The earlier [Adafruit PA1010D candidate](https://learn.adafruit.com/adafruit-mini-gps-pa1010d-module/pinouts) has 3.3 V TX output and default 9600 8N1, but is neither assumed purchased nor recommended for this iteration.

The vendor LVGL driver allocates two `floor(412×412/20)` pixel buffers in PSRAM, totaling **33,948 RGB565 bytes**; QSPI uses automatic DMA. This establishes a partial-buffer precedent, not a verified configuration for our renderer. JPEG decoder scratch, conversion buffers, TLS, driver queues, audio buffers and internal DMA-capable memory must be measured. Do not transplant the old 480² RGB-panel two-framebuffer budget. [Vendor LVGL buffer definition](https://github.com/waveshareteam/ESP32-S3-Touch-LCD-1.46/blob/fda89ff2ff32eb1bce561901225c6a36fa684237/example/ESP-IDF-5.3.2/ESP32-S3-Touch-LCD-1.46-Test/main/LVGL_Driver/LVGL_Driver.h), [allocation source](https://github.com/waveshareteam/ESP32-S3-Touch-LCD-1.46/blob/fda89ff2ff32eb1bce561901225c6a36fa684237/example/ESP-IDF-5.3.2/ESP32-S3-Touch-LCD-1.46-Test/main/LVGL_Driver/LVGL_Driver.c)

The portable networking implementation has host-measured sizes of **40 bytes for its controller, 292 bytes for configuration and 304 serialized NVS bytes**. Its IDF adapter configures one 6,144-byte health-worker stack and bounded queues; SDK Wi-Fi/TLS heaps remain unmeasured. These small control structures do not constitute the network memory budget. The current credential store is a local prototype, without NVS encryption or a production credential-protection claim.

The project limits the SDK HTTP parser to **4 KiB of headers**; callback validation happens too late to provide that allocation bound by itself. Updating the SDK does **not** establish a hard request deadline: socket timeouts are per operation, and header reads can outlast the nominal deadline. During bring-up, repeatedly interrupt headers/downloads and reconnect while recording free heap and the largest free block.
